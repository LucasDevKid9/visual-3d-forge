## 1. 一句话结论

[`VALIDATION.md`](VALIDATION.md) 已经诚实地写下了这个边界：

> 「校验器能抓 API 幻觉与白屏，抓不到『零件插进另一个零件』——那要靠人眼看，或靠包围盒自检。本仓库目前只能靠人眼……」

下游项目用一次真实返工验证了这句话的代价，也验证了**「包围盒自检」这一半是可以工程化、可以进 CI、可以把人眼彻底替掉的**。
补上它之后，该项目的几何缺陷从 **574 处（大量假阳性混着真缺陷）收敛到 0 处登记外干涉**，且四种构型各有门禁。

---

## 2. 现场：三类缺陷都通过了「能跑、能看、能转」的验收

下游首版交付了 179 个构件、37 项交互断言、920 kB 单文件产物、完整测试日志与已知限制清单。
从上游 `validate_scene.py` 的 19 项契约看，它几乎是全绿的。但用户指出的三类问题依然成立：

| 缺陷 | 具体表现 | 为什么现有校验抓不到 |
|---|---|---|
| **穿模** | 飞轮轮缘被误旋转成竖环，包围盒 3.1×3.1×3.0 m（实际应约 2.23 m 直径）；控制台宽 2.6 m 沿 x 布置，穿出舷侧板 | 契约校验看的是 API 真实性、离线、单文件、白屏，**不看两个实体在世界坐标里的空间关系** |
| **管线不合理** | 管路为自由曲线 spaghetti，无管夹、无法兰、不正交，穿凸轮轴与缸盖 | 「有管子」是素材事实，「管子怎么走」是工程约定，19 项里没有对应谓词 |
| **动力链断裂** | 燃机输出轴与减速齿轮箱之间悬空 1.8 m，缺换向与传动段 | 每个零件各自合法，**接缝无人负责**——没有表达「A 的输出法兰必须接到 B 的输入法兰」的真值表 |

这与 [`VALIDATION.md`](VALIDATION.md) 第四节记录的行星齿轮示例是同一类病：
「下压板随行星架整体上移重新盖住齿轮」「行星轮径向位移不足插进齿圈内壁」——
**零件都在、都能渲染、都不白屏，但它们互相插进去了**。

## 3. 六个失效机制（可迁移，不止 3D）

| # | 机制 | 在 3D 里的表现 |
|---|---|---|
| M1 | **知识不是约束** | 「注意不要穿模」写在提示词里，长链生成中必然衰减；`PENETRATE=0.18` + 顶点入体判定 + `exit 1` 才是约束 |
| M2 | **局部正确，全局无人负责** | 每个构件单独看都对，法兰之间的连接段没有任何数据结构声明 |
| M3 | **反馈通道带宽不足** | 截图是三维场景的二维投影，遮挡与深度信息丢失；「看着像」替代「算得出」 |
| M4 | **隐性默认值 + 结构化复制** | 同一轴线坐标在 5 个文件里各写一遍，改一处其余漂移 |
| M5 | **数量型 KPI 挤压空间预算** | 「构件数 / 面数」被当成质量指标，穿模检测反而没人做 |
| M6 | **没有可重放的验收基线** | 每次靠人工重看截图，无法 diff、无法进 CI、无法防回归 |

返工公式（够用即可）：

```
返工概率 ≈ (跨模块共享的量 × 复制份数 × 只靠人眼验收的环节) / 机器可判定的约束数
```

首版的分子很大、分母接近零，所以「用户没让返工，但成果必然需要二次返工」。

## 4. 建议增加的硬规则（可直接写进 `SKILL.md`）

### R1 · 单一真值表：跨构件的装配关系只写一次

`G2 参考闸` 判定的是「参考图可信度」，`G3 预算闸` 判定的是「面数 / draw call」，
但两者都不表达**装配拓扑**。建议在 G3 之后增加一道**关系闸**：

产出的不是又一张表，而是一份**可被程序反查的声明**：

```js
// 下游项目 src/core/driveline.js（8 节点 / 7 段 / 2 自由端）
NODES    = { 'pt-flange': {p, a, r, label}, ... }        // 法兰/轴端：位置 + 轴向 + 半径
SEGMENTS = [{ from, to, kind: 'shaft|gear|flex', parts: [...] }, ...]  // 声明由哪个构件实现
```

判据：**任何需要两个地方同时说对的量，必须只有一个出处**。
实现层引用节点坐标，不复制坐标；验证层沿段采样，反查实现件几何是否覆盖。

### R2 · 审计优先：交付前必须跑机器可判定的谓词，不能只看截图

建议在 `validate_scene.py` 之外补一层**几何关系校验**，至少五类：

| 检查 | 谓词 | 下游实现 |
|---|---|---|
| 干涉 | 实体子网格级盒相交 + 顶点入体深度 > 阈值 | `src/core/audit.js` |
| 走管 | 管线顶点侵入块体设备（排除骨架/格栅、排除管对管） | 同上 |
| 传动链覆盖 | 每段取 14 个采样点，实现件几何必须覆盖 | 同上 |
| 节点吻合 | 相邻段共享节点的构件中心距 ≤ `max(0.25, r×1.2)` | 同上 |
| 长跨支承 | >3 m 的旋转轴段，中点 55% 段长内须有声明的支承件 | 同上 |

**两个关键工程细节**（下游踩过坑，值得直接抄）：

1. **不要用整件包围盒做干涉判定**。按材质全合批会把整段管系压成一个巨型 AABB，
   「管子穿过机器」和「管子贴着机器走」无法区分。要在合批**之前**把每个实体子网格的
   包围盒留档（下游是 `group.userData.solidBoxes`），审计读留档盒——
   于是**渲染合批粒度与审计空间精度彻底解耦**，分块从 1.6 m 放大到 5 m，
   draw calls 从 2,628 降回 1,982，审计结论不变。
2. **镂空骨架要排除**。平台 / 格栅 / 围栏 / 桥架的 AABB 横跨整个机舱，
   不排除会把所有走管都报成穿模（下游曾误报 4,956 个顶点）。

### R3 · 豁免表可审计，禁止调大阈值放水

轴穿轴承、叶根坐入桨毂、艉轴穿艉管在几何上必然重叠，**属于装配而非缺陷**。
但不能用一个大阈值把它们一起放过——那会把真缺陷一起放过。

要求逐条登记 `{a, b, reason}`，双向匹配，且**理由必须是工程语言**（下游 51 条，
见 [`AUDIT-ALLOW.md`](https://github.com/LucasDevKid9/marine-propulsion-3d/blob/main/docs/AUDIT-ALLOW.md)）。
配套两条机制：

- 文档由源码数组自动生成（`npm run docs:allow`），人工不维护第二份清单；
- CI 执行 `git diff --exit-code docs/AUDIT-ALLOW.md`，改了源码没重生成文档就失败。

**豁免只能作用于干涉/走管；拓扑连通性、节点吻合、链图不可豁免。**

### R4 · 确定性验收：一条命令、非零退出、可挂 CI

```bash
npm run lint:geom     # 四种构型各跑一遍，干涉上限 0，任一非空 exit 1
```

下游四种构型（主机 × 推进器）实测：干涉 0 / 走管异常 0 / 传动链空洞 0 / 节点失配 0 / 链图 OK。
构型矩阵很重要：**只在默认构型下验收，等于只验收了 1/4 个产品**。

## 5. 建议给生成类 Skill 补的「四件套」

| 组件 | 作用 | 下游可直接复用的实现 |
|---|---|---|
| 真值表模板 | 跨模块共享量只有一个出处 | [`driveline.js`](https://github.com/LucasDevKid9/marine-propulsion-3d/blob/main/src/core/driveline.js) |
| 审计脚本骨架 | 把「正确」变成可执行谓词 | [`audit.js`](https://github.com/LucasDevKid9/marine-propulsion-3d/blob/main/src/core/audit.js) |
| 门禁命令 | 一条命令、非零退出、挂 CI | [`geom-lint.mjs`](https://github.com/LucasDevKid9/marine-propulsion-3d/blob/main/scripts/geom-lint.mjs) |
| 豁免表格式 | 例外显式、可审计、可复核 | [`audit-allow.js`](https://github.com/LucasDevKid9/marine-propulsion-3d/blob/main/src/core/audit-allow.js) |

配套的可复用思路：**所有清单类文档从运行时数据生成并做 diff 校验**
（`PARTS.md` / `parts.json` 亦然）。下游首版的 `PARTS.md` 手工维护，
构件数停在 179 而代码已到 186 —— 与几何穿模是同一个病：**产物与真值源不同步**。

## 6. 一个反直觉的结论

首版不是偷懒：它把几乎全部工程预算花在了「生成」上，几乎没有花在「校验」上。
在这类任务里：

> **校验才是主体工程，生成只是素材准备。**

下游本轮新增的代码里，审计器（`driveline.js` + `audit.js` + `audit-allow.js` + `geom-lint.mjs`）
比新增的几何构件更值得写——几何只解决这一次，审计解决之后的每一次。
Skill 的角色因此从「提醒你别犯错」变成**「让你无法交付一个错误的东西」**。

---

## 7. 建议的落地顺序（最小侵入）

1. 先在 `docs/VALIDATION.md` 第四节把那句「目前只能靠人眼」更新为「已有可复用的包围盒自检方案，见本文件」，并链到本文；
2. 在 `validate_scene.py` 增加**可选**的 `--geometry` 模式（不改动现有 19 项契约的默认行为），输出五类检查 JSON；
3. 在 `SKILL.md` 的 G3 之后增加「关系闸」，要求输出 `NODES/SEGMENTS` 声明（哪怕是空表，也要显式写「本场景无传动链」）；
4. 在契约清单里增加一条反向用例：**故意让两个实体互相插入 0.3 m，校验器必须变红**。
   上游 [`VALIDATION.md`](VALIDATION.md) 的反向用例清单已经证明了这个思路的价值——
   只测「对的时候对」等于没测。

---

## 8. 适用范围（不止 3D）

同样的「接缝无人负责」出现在：多章节长文档（第 3 章结论与第 7 章数字对不上）、
多表联动 Excel（汇总口径与明细不一致）、前后端联调（字段名/单位不一致）、
汇报 PPT（正文 3 个方向、附录 4 个）、多文件重构（改了 A 忘了镜像的 B）。

判断标准只有一条：**这个量，是不是需要两个地方同时说对？如果是，它就必须只有一个出处。**
