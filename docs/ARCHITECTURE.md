# 架构：一个把参考图编译成网页的编译器

这份文档说明 `visual-3d-forge` 的内部结构，以及每个结构为什么必须存在。
如果只读一段，读第一节——**这个 skill 不是提示词模板，是一条编译流水线**。

---

## 一、中心命题：它是编译器，不是提示词

绝大多数「AI 做 3D」的做法是：把需求塞进一段很长的提示词，让模型直接吐 HTML。
失败方式也很固定——**出来的东西能转，但不像那个物体**。

原因不在模型不够强，而在**中间表示（IR）缺失**：模型从「一句话」直接跳到「`new THREE.Mesh`」，
中间没有「这东西由哪些零件构成、每个零件多大、什么材料」这一层。
没有 IR，模型只能从训练分布里取最像的模板，于是所有物体都长成同一个光滑的盒子。

本 skill 的解法是把这件事拆成编译器的四段：

```
        前端                    中端                      后端                验证
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐   ┌──────────┐
│ 意图解码 P0      │   │ 算法装配 P2/P3   │   │ 代码生成 P4      │   │ 验收 P5  │
│ 参考解构 P1      │──▶│ 算法图谱 → 策略表 │──▶│ D0/D1/D2/D3 四目标│──▶│ 19 项检查 │
└──────────────────┘   └──────────────────┘   └──────────────────┘   └──────────┘
        │                       │                       │
        ▼                       ▼                       ▼
   意图卡 + 构件树          几何/材质/光照/运动      可运行的单文件或工程
   尺度表 + 材质假设         算法清单 + API 核对
        └───────────── IR ─────────────┘
```

**IR 就是 P1/P2 的产物**：构件树 + 尺度表 + 材质假设表 + 几何策略表。
它不写给用户看，但它决定了后面所有代码的形状。这也是为什么 `SKILL.md` 敢写死一条纪律：

> P1 未完成不得进 P4。

---

## 二、前端：三个把「模糊」压成「可计算」的装置

### 1. 意图卡（七字段）

对象 / 目的 / 受众 / 尺度 / 必须出现的要素 / 可以舍弃的要素 / 交付形态。

七个字段的作用不是收集信息，而是**消灭自由度**。"做个酷炫的产品页" 有无限种解读；
填完七字段后，只剩一种。缺任意一项就不算通关——这是 `G1` 的判据。

### 2. 参考可信度分级（R1–R5）

| 等级 | 来源 | 能推出什么 |
|---|---|---|
| R1 | 工程图 / 三视图 / 带尺寸 | 真实比例、隐藏轮廓 |
| R2 | ≥3 视角照片 | 近似形体 |
| R3 | 单张照片 | 主轮廓、材质质感 |
| R4 | 草图 | 设计意图 |
| R5 | 纯文字 | 类别先验 |

分级的意义是**给「精度」定一个可辩护的上限**：R3 以下不许说"精确还原"。
这条规则直接对应十条红线里的第一条「精度谎言」——它不是道德要求，是**认知诚实的技术化**。

### 3. 尺度表

所有尺寸从一张表派生，禁止在代码里散落魔法数字。
`assets/scaffold/forged-scene.html` 里 `const S = { H: 0.46, Rmax: 0.19, ... }` 就是范例：
换一个物体只改这张表，管线不动。

---

## 三、中端：算法图谱解决「知道要什么，不知道怎么算」

`04-algorithm-atlas.md` 按问题组织（几何 / 材质光照 / 运动 / 交互 / 工业 / 性能），
`09-part-library.md` 给 27 个可抄构件，`10-material-recipes.md` 给数值配方。

这一层的设计判断是：**不要把「知识」写成原理，要写成可查表**。
模型不缺 PBR 的定义，缺的是"铝的粗糙度填 0.32、金属度填 1.0"这种能直接落笔的数。

---

## 四、后端：四种交付形态是四个 codegen target

| 形态 | 产物 | 实测体积 | 依赖 | 何时选 |
|---|---|---|---|---|
| **D0** | 1 个 `.html` | 13 KB | 联网（jsDelivr） | **默认** |
| **D1** | 1 个 `.html` | 2852 KB | 零 | 离线 / 内网 / U 盘 |
| **D2** | `.html` + `vendor/` | 13 KB + 2391 KB | 零 | 要可读源码 |
| **D3** | R3F 工程 | npm | 构建链 | 与 React 应用联动 |

这一层的技术难点只有一个，但很硬：**D1 的 data URL 模块没有目录概念**。
`three.module.js` 内部 `import './three.core.js'`，在 data URL 里会解析失败 → 白屏。
所以 `bundle.py` 必须递归内联整个相对依赖闭包，并把它们改写成 `vf-int-N` 这样的 bare specifier。

`v2.0.1` 修的就是这里的去重缺陷：同一依赖被 `import` 与 `export ... from` 各引用一次时，
第二个仍自增编号，产出未注册的 `vf-int-2` → 白屏。**这是本仓库最有价值的一条历史记录**：
它证明这套工具是被真实失败打磨出来的，不是设计出来的。

## 五、验证层：两张网，两种盲区

### 网一：API 真实性（`api_lookup.py`）

从 three 源码递归解析 export 链建符号表（488 项），把产物里所有 `THREE.X` 与
`three/addons/...` 路径做差集，给出最接近的正确名。

它防的是**幻觉 API**——三维任务里最贵的一类错误：不报语法错，只白屏。

### 网二：静态契约（`validate_scene.py`）

19 项（D1）/ 18 项（D0、D2），覆盖交付形态、importmap 完整性、内联闭包悬空 specifier、
色彩管理单次性、像素比封顶、三光结构、接触阴影、相机限位、WebGL 兜底、后台停渲染、
三角面预算、材质分裂、R3F 反模式。

它防的是**结构性错误**：那些"看起来能跑，但一定会在某台机器上坏掉"的写法。

### 两张网都防不住什么

> 静态检查能证明「这个页面不会白屏、不会发灰、不会穿模」，不能证明「它好看、像那个物体」。

这是本仓库最诚实的边界。判断"像不像"仍然只能靠人眼，或靠参考图并排比对。
所以 `08-qa-delivery.md` 的 12 项验收清单里，前几项是给人看的，不是给脚本看的。

## 六、依赖关系与加载策略

```
SKILL.md  ──索引──▶ references/*.md        按阶段按需读，不一次性加载
    │
    ├──调用──▶ scripts/*.py                纯标准库，无第三方依赖
    │              ├── vendor.py           裁剪 three → vendor/
    │              ├── bundle.py           vendor → 单文件
    │              ├── api_lookup.py       查符号真实性
    │              └── validate_scene.py   交付前自检
    │
    └──复制──▶ assets/scaffold/*           从骨架起，不在空白文件里手写管线
                   └── assets/vendor/*     three 0.187.0 的 18 文件裁剪集
```

三条硬约束：

1. **版本固定 `0.187.0`**，三档之间不混版本。版本漂移是最难排查的一类坏法。
2. **脚本零第三方依赖**（`tests/test_contract.py::test_脚本只用标准库` 会验证）。
3. **骨架必须先跑通再换主体**。空文件起手 = 把五个已知坑重新踩一遍。

## 七、失效模式对照表

每一行都是"跳过某一步"的确定代价：

| 跳过 | 症状 | 根因 |
|---|---|---|
| G0 载体闸 | 用 WebGL 展示一个 2D 就能说清的事 | 没问"第三维承载什么" |
| P1 参考解构 | 物体由无名盒子拼成、比例失真 | 没有构件树，只有形体轮廓 |
| P2 建模方案 | 一半构件"待定"，最后靠堆图元糊过去 | 没有几何策略表 |
| P3 API 查证 | 白屏，控制台 `undefined is not a constructor` | 记忆里的 API 不存在 |
| G4 依赖闸 | 断网白屏、路径 404 | 交付形态与运行环境不匹配 |
| G3 预算闸 | 低端机 5 fps | 面数与绘制调用无预算 |
| P5 校验 | 交付后才发现相机能穿进物体 | 没跑 19 项检查 |

这张表是给"急着写代码的人"看的：**每一个跳步都有名字、有症状、有根因**。

## 八、边界（不粉饰）

1. **静态检查管不了审美**。19 项全绿 ≠ 好看。
2. **`api_lookup.py` 需要 three 源码**（`npm pack three@0.187.0`）。本包只带 build 产物，
   开箱时这一闸跑不起来——这是已知缺口，不是 bug 掩盖。
3. **没有自动化的视觉回归**。没有参考图与渲染结果的像素级比对。
4. **`vendor/` 提交了 2.4 MB 二进制**。换来的是零网络、零构建的离线可用；
   代价是仓库体积与 three 升级时的重新生成成本。
5. **技能正文为中文**。英文用户只能靠 `description` 与代码结构理解，没有英文版 SKILL.md。
6. **D3 只给骨架与陷阱表**，不给完整的 R3F 工程范式。它假设使用者已经会 React。
