# 06 · 体验：确认件该拿哪一只角

> v3 带来了一整套「体验导演层」——六段式、十幕法、BPM 栅格、Web Audio、游戏化引导。
> 这一章的任务不是把它搬进来，是**判断哪一部分属于确认件，哪一部分必须挡在门外**。
>
> 判断本身比结论重要：同样的推理可以套到下一个项目上。

---

## 一、先判定：确认件是"展示型"

判据来自 `SKILL.md` 的 G5 体验闸，三个问题：

| 问题 | 确认件的答案 |
|---|---|
| G5-1 用户为什么点进来？ | 他要核一件事：装配顺序对不对、总长多少、哪个数是猜的 |
| G5-2 他反复做的那件事是什么？ | **看**。凑近、转一下、点开一条尺寸 |
| G5-3 结束时他手里多了什么？ | 一句「可以签」，或者一份「这里有 3 项未确认」的清单 |

三条都指向同一个结论：**展示型**。

G5 的反例警报在这里正好成立——如果 G5-2 的答案是「看」，那任何要求用户「等」的设计都是成本。确认件的用户不是来被娱乐的，他是来交差的。

---

## 二、明确否决的四件事

v3 里最好的那些东西，对确认件恰恰是错的：

| 否决 | 为什么 |
|---|---|
| **不做音效** | 声音是节拍器，服务于情绪推进。确认件没有情绪曲线，加声音只是给评审添噪音 |
| **不做结算页 / 成就** | 「你已看完 10 个构件，获得拆解大师称号」——这句话在工程评审会上会让人怀疑整份文件的严肃性 |
| **不做十幕法** | 十幕是为品牌体验设计的。确认件的全部旅程是：看见 → 拆开 → 收束，三幕 |
| **不做主题切换** | 换一个环境色，会让人怀疑数据是不是也跟着换了。确认件的环境必须稳定 |

> 这四条不是「保守」，是从 G5-2 直接推出来的。**判断标准只有一句：这个功能帮谁确认了什么。** 答不上的，就是装饰。

---

## 三、展示型也能拿的四样

v3 里有四样东西，跟「体验型」无关，只跟「做得细不细」有关。

### 3.1 三幕开场（6–10 秒，可跳过）

幕数决策表里，**单一物体展示 = 3 幕（呈现 / 拆解 / 收束），20–30 秒**。

确认件现在没有"幕"，打开就是一个静态场景加一个可拖的滑块。缺的是**第一眼**：让人在 3 秒内知道「这是什么、多长、几件」。

最小实现不是做动画片，是：

1. **呈现**：模型已在位，相机轻转 3 秒（现在有，但没经过 reduced-motion 判断）
2. **拆解**：不自动播。留给用户拖滑块——因为**他来看的就是这个**
3. **收束**：不需要"结算页"，一行常驻的覆盖率数字就是收束（现在底部已有）

结论：**确认件的"三幕"里只有第一幕需要做，且已经在做。** 别为了凑幕数硬加第二、三幕。

### 3.2 时长吸附到 BPM 栅格

```js
const BPM = 120;                      // 1 拍 = 0.5 s
const beat = 60 / BPM;
const snap = (s, sub = 2) => Math.round(s / (beat / sub)) * (beat / sub);
```

原来相机飞行的时长是 `620` 这个魔数，散落在两处。现在统一为 `MOTION.fly = 500`（正好 1 拍），曲线也命名了。

**为什么值得改**：不是因为 500 比 620 好看，是因为「一个页面里所有动效取同一个时间栅格」这件事，决定了观感是「整体」还是「拼的」。

### 3.3 微反馈 : 叙事转场 ≈ 2 : 1

v3 从样本 C 数出来：44 个 keyframes 里 30 个是微反馈，14 个是叙事转场。

确认件的现状是**微反馈几乎为零**——所有变化都是状态切换，没有过渡。hover 变个色、选中亮一下，就是全部。

不需要加很多。**3–5 处**就够：列表行 hover、尺寸线选中、滑块拖动、视图切换按钮。有了它们，页面才"活着"；多了，就变成"全程都在动 = 什么都不突出"。

### 3.4 加载不是等待，是第一章

确认件产物 2.8 MB（D1 形态）。首次解析时的白屏，是用户对这份东西的第一印象。

三种做法（v3 的样本各用一种）：显示百分比 / 做成仪式 / 当第一幕。

确认件选第一种就够：**一行字 + 一个进度**，300ms 内出现。不要做成仪式——那属于体验型。

## 四、把 23 项体验自检当检查表用

`scripts/validate_experience.py` 有 23 项（X01–X23）。它本来是给体验型产物写的，但其中若干项跟"体验"无关，只跟"做得对不对"有关。

**拿它扫确认件，得到了一张真实的缺陷清单。**

### 4.1 改之前

```
通过 4 · 警告 9 · 失败 4
```

失败的四项：

| 项 | 症状 | 是不是真缺陷 |
|---|---|---|
| X09 缺 `visibilitychange` | 切到后台仍渲染，烧电 | **是**。跟体验层无关，纯工程问题 |
| X10 缺 `prefers-reduced-motion` | 用户开了"减少动态"，开场照转 | **是**。前庭敏感的用户会不适 |
| X02 无幕结构 | — | 否。展示型不需要幕 |
| X23 无键盘支持 | 只能靠鼠标点构件 | **是**。等于把"核对"限定在有鼠标的场景里 |

### 4.2 改了什么

| 项 | 改动 | 位置 |
|---|---|---|
| X09 | `visibilitychange` 时置 `paused`，`tick` 直接 return | `viewer.js` 渲染循环 |
| X10 | 读 `matchMedia('(prefers-reduced-motion: reduce)')`；为真时**不转**（不是转慢），相机飞行时长压到 1/4 | `viewer.js` `MOTION` |
| X13 | 开场 3.2 秒自动停，本身即"跳过"；无更长动画故不另设按钮 | — |
| X14 | 所有 `:hover` 收进 `@media (hover: hover) and (pointer: fine)` | `viewer.css` |
| X15 | `.sv-head` / `.sv-dock` 用 `env(safe-area-inset-*)` | `viewer.css` |
| X18 | 5 条 `--ease-*` + 2 条 `--t-*` 自定义属性，CSS 过渡全部改用 | `viewer.css` `:root` |
| X19/X20 | `BPM = 120`，`MOTION` 由它推导时长 | `viewer.js` |
| X23 | `Esc` 回到全局（清选中 + 飞回 iso），方向键遍历尺寸 | `viewer.js` keydown |

### 4.3 改之后

```
通过 12 · 警告 4 · 失败 2
```

**从 4 过到 12 过，其中五项是真正的缺陷修复，不是"为了让检查变绿"。**

剩下的 2 个失败，逐条说明为什么**保留红灯**：

| 项 | 为什么不算缺陷 |
|---|---|
| X01 未发现状态机 | 检测器找的是 `Machine.register() + go()` 这套 v3 专用 API。确认件的状态是 `{explode, section, hover, activeDim}` 四个数，上完整状态机是过度工程。**红灯在这里表示"方言不同"，不是"缺能力"** |
| X02 未发现幕结构 | 展示型判定下不需要幕。这一条对确认件是**不适用**，不是**未通过** |

> **不为了变绿去改检测器**。让检测器认识我们的方言，等于把"检查"改成"背书"，那时它就不再是检查表了。
> 正确做法是像上面这样：**留红灯，写清楚为什么留。**

## 五、什么情况下才该升级成体验型

有一条清晰的分界线：**用户是不是被"请"来的。**

| 场景 | 判定 | 动作 |
|---|---|---|
| 客户内部评审、图纸确认、装配顺序核对 | 展示型 | 只做本章第三节的四样 |
| 展会大屏、新品发布、对外宣传页 | 体验型 | 走完整 E1/E2，读 [`../references/18-experience-architecture.md`](../references/18-experience-architecture.md) |
| 前 5 秒抓人，之后让人自己查 | 混合型 | 前 3 幕体验化，之后转工具箱 |

一个具体的混合型例子：**如果把确认件放进招商材料**，前半段可以是 8 秒的"从图纸到装配"快剪，后半段立刻交还控制权。这时 E1 只做三幕，E2 只定 BPM。

但要先想清楚一件事：**加了体验，就没有人再敢拿它签字了。** 一份会放音乐的工程文件，在评审会上是要被质疑的。

---

## 六、这一章的方法论

v3 给的不是"更多功能"，是一套判定工具。它的正确用法是**用来拒绝**：

- G5 判出展示型 → 拒绝了音效、结算、十幕法
- 23 项自检 → 找出了 5 个真缺陷（其中 4 个跟"体验"毫无关系）

> 一份方法论最大的价值，不是它教会你做什么，是它**替你挡掉了什么**。
