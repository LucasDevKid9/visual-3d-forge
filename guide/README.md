# 从一张图到一件成品 / From a Drawing to a Deliverable

> 这份引导来自一个真实项目的沉淀：NOVA X-01 实时试验台。
> 它的原始形态是两份给 AI 的系统指令——一份内核（OMNIFORGE）、一份案例包（RCP-001）。
> 两份都在仓库外，因为它们写成了「指令」，只有机器读得进去。
>
> 这里做的是把它们**改写成给人用的东西**：可以填的模板、可以核的判据、可以走通的例子。
>
> This guide comes out of a real project. Its original form was two system prompts written
> for machines. What follows is the same knowledge rewritten for people: fillable templates,
> checkable gates, and one worked example you can follow end to end.

---

## 一、先说清楚：这份引导教什么，不教什么

**教的是「怎么把需求说到可以被执行」，不是「怎么建模」。**

这条边界和本项目的主线是同一个判断：模型每年都在变强，能吃掉的是「写 three.js」和「猜物体长什么样」；吃不掉的是「从图里判断 160 是外径不是长度」「让 12 个尺寸互相自洽」「说清哪个数是猜的」。后者不是能力问题，是**责任归属问题**。

所以这份引导的重心全部压在前半段：读图、抽取、定成色、写契约、定判据。代码那一段它只给结构，因为代码已经有人比我们写得好，而且明年会更好。

> 一句话：**我们不教你画，我们教你把你想要的东西说清楚到不需要返工。**

## 二、三层结构：为什么单靠任何一层都会退化

原始案例包的核心洞察值得原样保留。它把一套能移植的标准拆成三层，缺一层就退化成不同的东西：

| 层 | 是什么 | 缺了会怎样 |
|---|---|---|
| **内核** | 系统性的思考方式：分类 → 解码 → 规格 → 装配 → 蓝图 → 实现 → 验证 → 精修 | 会思考，但不知道你要的达标线在哪 |
| **契约** | 结构 + 约束 + 验收判据，把「好」写成可判定 | 知道要求，但没见过成品长什么样 |
| **实证** | 一份跑得起来、看得见的母本 | 会模仿外形，但不懂背后的系统 |

三层构成「思考 → 契约 → 实证」的闭环。缺任何一层，换一个 AI、换一个主体，标准就会掉。

**本仓库里，这三层的对应物是：**

| 层 | 在仓库里的位置 |
|---|---|
| 内核 | 就是这份 `guide/`，加上 [`../docs/PRINCIPLES.md`](../docs/PRINCIPLES.md) 的十条工程原则 |
| 契约 | [`01-BRIEF.md`](./01-BRIEF.md) / [`03-SPEC.md`](./03-SPEC.md) / [`04-VERIFY.md`](./04-VERIFY.md)，以及 `spec/schema/specsheet.schema.json` |
| 实证 | [`../spec/out/nema23-actuator.html`](../spec/out/nema23-actuator.html)（线上可开）与 [`../spec/out/nema23-actuator.report.html`](../spec/out/nema23-actuator.report.html) |

## 三、三种人，三条路

### 路 A · 我只是想评估这东西靠不靠谱（10 分钟）

1. 打开 [`../spec/out/nema23-actuator.html`](../spec/out/nema23-actuator.html)，随便点几个零件，看尺寸线跟着亮不亮
2. 打开 [`../spec/out/nema23-actuator.report.html`](../spec/out/nema23-actuator.report.html)，看 C1–C6 六项检查各自的判据
3. 读 [`../docs/PRINCIPLES.md`](../docs/PRINCIPLES.md) 的第一条和第八条

如果第 2 步的报告里，有一项数字你**不认同它的来源标注**——那说明这套东西是可被否证的，这是它唯一的价值证明。

### 路 B · 我要拿它做自己的第一件（半天）

按顺序走，别跳：

1. [`01-BRIEF.md`](./01-BRIEF.md) —— 把你的想法填成一张需求表（20 分钟）
2. [`02-DECODE.md`](./02-DECODE.md) —— 对着你的图，把每个数标上来路（40 分钟）
3. [`03-SPEC.md`](./03-SPEC.md) —— 填成一份 SpecSheet，跑一次编译（60 分钟）
4. [`04-VERIFY.md`](./04-VERIFY.md) —— 过门禁，没过就回第 3 步

走不下去的时候看 [`WALKTHROUGH.md`](./WALKTHROUGH.md)，那是一份真实的填表记录，包含**填错的那几版**。

### 路 C · 我要把这套方法搬到别的主体上（不限时）

先读 [`WALKTHROUGH.md`](./WALKTHROUGH.md) 的「哪些是可替换的，哪些不是」一节。核心纪律只有一条：

> **学它的系统，不学它的外壳。**
>
> 母本给你的价值在结构——五基元怎么分工、证据怎么分三档、约束怎么互相咬。不在「一台减速电机」这个具体形状。

## 四、这套东西的原始形态，和我们的改造

原始两份文档的体量与野心都很大：内核 22 节，覆盖八类工件（3D 主体 / 工业链 / 动画 / 数据 / 网站 / WebApp / 游戏 / SVG）；案例包 7 个文件，含槽位化 Prompt 框架、13 条故障码、5 组补丁提示词。

我们**没有全盘收编**。取舍如下：

| 原文档里的 | 我们的处理 | 理由 |
|---|---|---|
| 八类工件的分类学 | 只保留「3D 主体」一类 | 我们是确认件，不是通用工件引擎。宣称全能等于没有一处够深 |
| 十二域系统架构 | 收进 [`03-SPEC.md`](./03-SPEC.md) 的检查清单 | 作为「有没有漏」的核对表，而不是「必须全上」的指标 |
| 槽位化 Prompt 框架 | 改写成**给人填的** [`01-BRIEF.md`](./01-BRIEF.md) | 人填表比写 prompt 可靠；prompt 的槽位人看不懂 |
| 13 条故障码 | 保留，转成确认件语境，见 [`05-DIAGNOSE.md`](./05-DIAGNOSE.md) | 这是真经验，症状→域→根因→补丁的映射关系不能丢 |
| 18 条验收门禁 | 保留并逐条补上判据，见 [`04-VERIFY.md`](./04-VERIFY.md) | 原版只说「要有」，没说「怎样算有」。补判据才算可核 |
| 5 组补丁提示词 | 收进 [`05-DIAGNOSE.md`](./05-DIAGNOSE.md) 的「补丁」一节 | 同上，改成可操作的修改指令 |
| 「不得输出分析」「静默执行」等输出纪律 | **丢弃** | 那是给 AI 的运行时约束，对人没意义，对本仓库无价值 |

> 判断依据：一份文档的价值不在它说了多少，在**它敢删多少**。凡是「说了但无法被检验」的条目，都是在稀释约束力。

## 六、一条纪律，写在最前面

**填不出来的地方，写「不知道」，不要写一个看起来合理的数。**

这五个字是本项目所有其他纪律的前提。一个标着「不知道」的字段，会让下游的人去问你；一个编出来的数，会让下游的人以为已经问过了。

我们做的是确认件——**确认的前提是承认哪些还没被确认。**
